GoCommerce ↔ Svelte Commerce connector

Status: In development. Not published.

There is no installable package. You cannot point Svelte Commerce at GoCommerce today by changing a dependency, and nothing on this site claims otherwise.

This page exists so the answer is one link rather than an inference. It will become the connector’s documentation when there is a connector to document.

Current architecture

Both halves exist and are solid. The piece between them is the gap.

Svelte Commerce

Calls a connector package. Imports none by name — $connector resolves from package.json.

the missing piece — a package mapping 43 services onto the GoCommerce API

GoCommerce

Serves 342 documented operations over REST, published as OpenAPI.

Svelte Commerce reaches every backend through a connector implementing a shared 43-service surface — product, cart, checkout, order, auth, address and the rest. 26 of them exist. A GoCommerce connector is the twenty-seventh, and it is the one that is not written.

What exists, what does not

  • Done — in a repository today
  • In progress — being written now
  • Planned — not started
  • The GoCommerce API it would call — 342 operations, all in OpenAPI, with a documented contract per route. Nothing about the backend is blocking.
  • The connector interface it would implement — a 43-service surface, already implemented 26 times over, so the shape is settled rather than speculative.
  • The switching mechanism — Svelte Commerce resolves its connector from package.json, with PUBLIC_CONNECTOR to override. No storefront change is needed to adopt a new one.
  • The connector package itself — mapping GoCommerce’s routes onto those 43 services. This is the work.
  • Published to npm — as @misiki/gocommerce-connector, following the naming of the other 26.
  • A verified end-to-end path — a storefront running against a GoCommerce instance, with cart, checkout and auth exercised rather than asserted.
  • Setup documentation — which environment variables, which GoCommerce version, what to expect.

Known limitations

Things that will still be true on the day the connector first works.

A stable contract, not a proven one

GoCommerce is 1.0, so the API a connector binds to will not move without a major version. What 1.0 does not supply is production mileage: no store is known to run it yet, so a connector will meet whatever the first real catalogue exposes.

Coverage will start partial

The other 26 connectors range from 9 to 39 of 43 services. A first GoCommerce connector will land somewhere in that range, not at the top of it.

No benchmarks either way

Nothing has been published about GoCommerce’s performance, so nothing can honestly be said about the pair’s. That stays true until somebody measures it.

How to help

  • Write services against the existing interface. The surface is documented by 26 prior implementations; Litekart and Vendure at 39/43 are the closest thing to a reference.
  • Start with the commerce path. Product, cart, checkout, order. Those four decide whether a store can transact at all; the rest is refinement.
  • Do not stub auth. The convention across every connector is to throw rather than mint a session — a stub that logs anyone in is an auth bypass, not a placeholder.
  • Exercise it against a real instance. The standing weakness of all 26 connectors is that none has been run against a live production store. Being the first would matter more than the code.

The backend carries 1,036 tests and a documented contract for every route, so a connector has something precise to build against.

Connector questions

Can I connect Svelte Commerce to GoCommerce today?

Not with an installable package. The connector is in development and unpublished. GoCommerce serves a documented JSON API with 342 operations, so you can write the client yourself, but you would be writing it rather than installing it.

When will the connector be ready?

There is no date, and publishing one we cannot hold to would be worse than saying so. The work is a package mapping GoCommerce routes onto the 43-service connector surface; progress is visible in the repositories rather than announced here.

What is blocking it?

Nothing structural. The backend API exists and is documented, the connector interface is settled across 26 implementations, and the switching mechanism needs no storefront change. What is missing is the package itself being written and verified.

Will it be called anything in particular?

It will follow the existing naming, so @misiki/gocommerce-connector, matching the other 26 packages. Installing it and removing the previous connector is the whole switch.

Does this mean the two projects are not really a stack?

Today they are two good projects rather than one wired stack, and this page exists so nobody has to guess which. Both are independently useful right now — GoCommerce behind any client, Svelte Commerce in front of 26 other backends.

Either project is useful today

The connector is the only thing on this site marked in development. Everything else either ships or is plainly marked as planned.
